# ИБ: объектная авторизация для Junior/Middle

Текущий предметный кейс для **Junior/Middle**: объектная авторизация и актуальность разрешения при использовании. Семейство `security:object_access`, версия задания `object-access-v1`, модель/эталон `object-access-model-v1`, рубрика `object-access-rubric-v1`. Версии не переименованы в версию API: они сохраняются в каждой выданной попытке.

Проверяется ограниченный JSON-артефакт, а не запуск пользовательских программ или реальная инфраструктура. Сложность является авторской; профессиональная квалификация человека этим описанием не удостоверяется.

## Различия уровней
| Уровень | Требуемое действие | Два исходных дефекта |
|---|---|---|
| Junior | Соединить все основания доступа и проверить права на конкретный объект | missing_object: reader видит чужой документ своего tenant. or_policy: OR позволяет обойти обязательные ограничения |
| Middle | Выполнить Junior; сохранить текущие права при изменениях и использовании раннего разрешения | cached_allow: кеш хранит старый allow. stale_use: ранний ticket используется после изменения прав |

Junior проверяет один текущий контекст, не кеш и промежуток до использования. Middle добавляет состояние документа и две политики свежести решения. Это разные действия, а не только разные имена/числа. Senior новым семейством не оценивается.

## Контракт одного контекста
Для доступа одновременно нужны:

- Активный токен: token.active именно true.
- Та же организация: subject.tenant == object.tenant; роль не обходит границу tenant.
- Право на объект: editor читает/меняет документы своего tenant; reader только читает собственный документ. Другие роли не имеют прав.
- Scope действия в token.scopes. Только read/write известны приложению; export запрещён даже при таком scope.

План Junior:

```json
{
  "require": ["token_active", "same_tenant", "object_permission", "action_scope"],
  "logic": "all",
  "unknown": "deny"
}
```

Допускается ограниченный неправильный план: отсутствие фактора, any вместо all, allow для неизвестного действия. Сервер проверяет последствия, а не буквальное совпадение с ключом. Порядок факторов несущественен; лишние факторы/поля, дубли, код и checks не принимаются.

Модель перебирает reader/editor/guest, read/write/export, совпадение tenant, владельца, активность и scope: 144 контекста Junior. Для Middle добавляются четыре состояния объекта, всего 576 контекстов. oracle напрямую применяет контракт и не получает план, его require или reference_answer.

## Middle: состояние и свежесть
```json
{
  "require": ["token_active", "same_tenant", "object_permission", "action_scope", "object_state"],
  "logic": "all",
  "unknown": "deny",
  "cache": "live",
  "use": "recheck"
}
```

active разрешает read/write, locked — только read, deleted и неизвестное состояние — ничего. Это ограничение дополняет, а не заменяет объектное право и scope.

| Политика | Значение |
|---|---|
| cache=live | Каждый authorize вычисляет решение по текущему контексту |
| cache=memoized | Решение сохраняется по subject.id/object.id/action, без актуальных token/scopes/tenant/owner/role/state |
| use=recheck | Требуется allow-ticket для той же идентичности запроса и новое разрешение по текущему контексту, обходя кеш |
| use=authorize_only | Используется прежний allow-ticket без повторной проверки прав |

Ticket связан с субъектом, документом и действием. Отсутствующий ticket или смена идентичности запроса запрещены независимо от выбранного use. Ранний deny не становится разрешением автоматически при получении новых прав: нужен новый authorize.

Между authorize/use модель изменяет активность токена, scope, tenant/владельца документа, роль, lock/delete. Проверяются запрет после каждого изменения, новое решение после восстановления и положительные сценарии. Восстановление token.active в учебной трассе обозначает восстановленный допустимый контекст; это не утверждение, что реально отозванный подписанный токен можно повторно активировать.

Recheck и использование атомарны **только в этой модели**. В настоящем сервисе нужен собственный механизм связи актуального решения с операцией. Выполненный заранее HTTP-запрос проверки прав не обеспечивает такой атомарности сам.

## Проверка и контрпримеры
decide исполняет выбранные факторы. oracle независимо вычисляет истинный допуск. execute применяет фиксированные изменения контекста и операции authorize/use; trace_oracle не использует кеш, use или представленный план. Решения сравниваются после каждой операции, не только в конце.

| Группа | Основание |
|---|---|
| sec_allowed_paths | Корректные положительные сценарии разрешены |
| sec_tenant_isolation | Чужой tenant запрещён даже editor |
| sec_object_authorization | Reader не читает чужой объект/не пишет; неизвестная роль запрещена |
| sec_scope_token | Нет scope или токен неактивен — запрет |
| sec_default_deny | Неизвестное действие запрещено |
| sec_object_state, Middle | Lock/delete/неизвестное состояние соблюдаются |
| sec_live_decision, Middle | Новый authorize использует текущие права, включая восстановление после deny |
| sec_use_recheck, Middle | Ранний ticket, текущие права и идентичность запроса проверяются при use |

Junior имеет пять групп, Middle — восемь. Балл — доля пройденных групп; автоматическое принятие требует всех. Отсутствие объектной проверки даёт 80%, но не проходит. Доверие раннему allow после отзыва даёт 87,5%, но тоже не проходит даже при разборе на 100%.

Контрпримеры:

- Reader/active/read scope/same tenant для документа другого владельца: deny; missing_object даёт allow.
- Editor со всеми scopes чужого tenant: deny. Роль не означает глобальный доступ.
- authorize=allow, затем revoke, затем новый authorize: deny; memoized возвращает allow.
- authorize=allow, перенос в чужой tenant, затем use: deny; authorize_only продолжает разрешать.
- locked/read собственного документа разрешён, locked/write запрещён; deleted запрещает оба действия.
- authorize=deny, права появились, затем use того ticket: всё ещё deny; новый authorize/use разрешён.

Оба варианта имен tenant и оба ID документа дают четыре окружения на каждый дефект, всего 16 сочетаний. Это техническое пространство проверки; случайная смена имён не доказывает содержательной уникальности.

## Дополнительное объяснение и пределы
Предметная рубрика сохраняет четыре критерия 0–3: корректность, независимые проверки, обоснование и пределы. Она служит дополнительной обратной связи, а не обязательным допуском текущей v3.

Junior различает аутентификацию, tenant, объектное право и действие. Middle объясняет, почему кеш или ранний ticket не заменяют актуальную проверку, и приводит переходы с ожидаемыми решениями.

Вопрос Junior: прямой ID вложения и связь с родителем. Вопрос Middle: временное разрешение внешнему рецензенту. Нужны ограниченные объект/действие/срок, отзыв и границы исключения.

Контексты доверенные и синтетические. Не проверяются выдача/подпись токена, реальные middleware/БД, распределённая атомарность, таймеры, аудит, сеть и полный пентест. Политика упражнения не заменяет безопасность рабочего приложения.

## Использование в текущей аттестации

Семейство является одним из доступных вариантов для указанного направления и уровня; все семьи не выдаются в каждой попытке. Основной маршрут 0.16.0 — `work_sample_v3_balanced`, программа `competencies-2026-10-v14`:9 объективных заданий по трём областям, исходный кейс, отдельный проверяемый перенос и необязательное объяснение.

Для автоматического успеха одновременно требуются среднее короткого теста ≥ 70%, каждая основная область ≥ 50% при заполненной квоте и все обязательные проверки исходного кейса и переноса. Частичный рабочий балл полезен для разбора ошибок, но не компенсирует провал обязательной группы. Успешная аттестация выдаёт предварительную категорию автоматически; тренировка и неуспех сохраняют прошлую.

После этого предметного кейса обязательный перенос выполняется в другом ограниченном рабочем контексте того же направления и уровня с самостоятельным JSON-артефактом. Приведённые выше вопросы к объяснению дополнительны и не заменяют этот этап. Ручной структурированный разбор необязателен и не меняет автоматический проход v3.

Условия, семейство, версии модели/рубрики и эталоны заморожены в попытке. Ранее выданные версии продолжают проверяться собственным исполнителем; неизвестная версия даёт техническую паузу с сохранением ответов. Паспорт не содержит исходные ответы, скрытые эталоны или контакты. Пороги, сложность и соответствие профессиональным уровням не откалиброваны на людях.
