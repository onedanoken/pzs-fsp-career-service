# Backend Senior: резерв, внешняя оплата и возврат

Текущий предметный кейс для **Senior**: терминальные состояния, срок, локальная фиксация и внешняя компенсация. Семейство `backend:reservation_settlement`, версия задания `reservation-settlement-v1`, модель/эталон `reservation-settlement-model-v1`, рубрика `reservation-settlement-rubric-v1`. Версии не переименованы в версию API: они сохраняются в каждой выданной попытке.

Проверяется ограниченный JSON-артефакт, а не запуск пользовательских программ или реальная инфраструктура. Сложность является авторской; профессиональная квалификация человека этим описанием не удостоверяется.

## Различающееся действие
Junior исправляет локальный контракт и отказ без изменения товара. Middle защищает остаток и запись резерва при конкуренции и прерывании локальной операции. Senior в этом кейсе согласует терминальное состояние заказа, истечение срока, подтверждение сообщения брокеру и внешний возврат. Он должен объяснить, какие гарантии обеспечивает локальная фиксация, какие зависят от провайдера и как восстанавливается неизвестный внешний результат.

Здесь нет пользовательского Python/SQL/shell, настоящего брокера или платёжного провайдера. Выполняется ограниченный JSON-план над локальной моделью. Разбор требует конкретного механизма и воспроизводимых событий; перечисление saga/outbox/idempotency само по себе не является решением.

## Контракт
Два заказа A/B удерживают по `quantity` единиц одного товара. Начальный свободный остаток — `available`; срок A — `deadline`, B — `deadline + 1`. У каждого заказа один проверенный платёж `p-A`/`p-B`. Количество 1–3, свободный остаток 0–3, срок 2–5: 48 сочетаний параметров для каждого дефекта, 96 исходных вариантов. Время целое, часы общие; проверяются значения до, на и после срока.

| Событие и сохранённое состояние | Требуемое действие |
|---|---|
| Callback оплаты, held, `now < deadline` | Перевести в paid; товар остаётся проданным |
| Callback оплаты, held, `now >= deadline` | Перевести в expired, вернуть товар и вместе с переходом сохранить намерение возврата |
| Callback оплаты, expired | Сохранить намерение возврата этого платежа; товар повторно не возвращать |
| Callback оплаты, paid | Не менять товар и не создавать возврат |
| Истечение, held, срок наступил | Перевести в expired и освободить товар |
| Истечение до срока или для paid/expired | Не менять состояние |

В зафиксированных данных paid/expired терминальны. Инвариант после каждого события: свободный остаток + товар в held + товар в paid = начальное общее количество. Черновые изменения внутри atomic до commit другим событиям не видны.

Локальное состояние и намерение возврата фиксируются вместе. Брокер не должен получить подтверждение незавершённого события. Доставку возврата нельзя считать завершённой до внешнего эффекта; потерянный ответ требует повторить стабильный ключ. Провайдер в этой модели возвращает один эффект для одного ключа и сохраняет ключи весь период проверки. Разные платежи требуют разных возвратов.

## Два исходных дефекта и контрпримеры
| Вариант | Дефект | Контрпример |
|---|---|---|
| `late_payment` | Первое правило оплаты held применимо при любом времени | При сроке 3 callback в момент 3 переводит заказ в paid, хотя нужны expired и сохраняемый возврат |
| `lost_refund` | Outbox помечается доставленным до вызова провайдера | Сбой после отметки, до внешнего эффекта: после рестарта запись уже done, возврат никогда не вызывается |

Дополнительные мутации проверяются по поведению: snapshot освобождает уже оплаченный товар в гонке; split оставляет частичный переход без намерения возврата; before_commit теряет входное событие после сбоя; ключ доставки создаёт повторные возвраты; постоянный ключ объединяет возвраты разных платежей.

## Эталон и разрешённый план
Пример корректного плана:

```json
{
  "payment": [
    {"states": ["held"], "time": "before_deadline", "steps": ["pay"]},
    {"states": ["held"], "time": "due", "steps": ["expire", "refund"]},
    {"states": ["expired"], "time": "any", "steps": ["refund"]}
  ],
  "expiry": [
    {"states": ["held"], "time": "due", "steps": ["expire"]}
  ],
  "read": "current",
  "transaction": "atomic",
  "ack": "after_commit",
  "refund_key": "payment",
  "dispatch_ack": "after_effect"
}
```

Выбирается первое совпавшее правило; без совпадения событие не меняет данные. `pay` устанавливает paid; `expire` устанавливает expired и прибавляет количество к остатку; `refund` создаёт outbox-запись. Операции сами не защищают прежнее состояние: это обязанность условий правила.

`read=current` моделирует сериализованное решение по товару/заказу с актуальным состоянием, `snapshot` — условия конкурентной пачки по общему начальному снимку. Это не утверждение о свойствах конкретной БД. `atomic` фиксирует действия вместе, `split` сохраняет каждое отдельно. `ack` определяет момент подтверждения брокеру. `refund_key` задаёт ключ конкретного платежа, доставки или один общий ключ. `dispatch_ack` определяет момент отметки доставки относительно внешнего эффекта.

При уже существующем ключе outbox сохраняет прежнюю запись, включая done. Провайдер дедуплицирует по тому же ключу. Подтверждённый ID доставки брокер не повторяет; новый ID того же callback может прийти снова.

Разрешены 1–4 правила на вид события, 1–3 различные операции в правиле; возврат допустим только в payment. Дубликаты ключей JSON, неизвестные поля/режимы, неверные типы, повторные состояния/операции и ответы длиннее 5000 символов отклоняются.

Эталон `oracle()` строит ожидаемые переходы непосредственно из контракта. Он не получает план участника, режимы доставки или сохранённый reference_answer и не вызывает интерпретатор действий. Сравниваются состояние и внешний эффект после каждого события, а не буквальное совпадение JSON. Эквивалентные перестановки непересекающихся правил и черновых атомарных действий принимаются.

## Проверки и сбои
Восемь групп проверяют срок оплаты, терминальные состояния, повторы callback, сериализацию, атомарность, подтверждение входного события, восстановление доставки и независимость возвратов двух платежей. Балл — доля групп, но автоматический этап принимается только при **всех** успешных группах. Поэтому 87,5% у `lost_refund` недостаточно для категории, независимо от балла разбора.

Для входного события проверяются сбой после каждой выбранной операции плана, до commit и после commit до подтверждения. Сравнивается сохранённое состояние сразу после сбоя и результат повторной доставки после восстановления. Для исходящих возвратов сбой помещается между внешним эффектом и отметкой; после рестарта повторяется доставка, проверяется число реальных модельных эффектов. Сценарии включают оба порядка работы двух платежей.

## Дополнительное объяснение и пределы
Предметная рубрика сохраняет четыре критерия 0–3: корректность, независимые проверки, обоснование и пределы. Она служит дополнительной обратной связи, а не обязательным допуском текущей v3.

Объяснение связывает терминальные состояния и границу срока, атомарность локальной операции, подтверждение после commit, стабильный ключ возврата и повтор после неизвестного внешнего результата. Для гонки/сбоя нужны независимые ожидаемые остатки, намерения и эффекты.

Вопрос: провайдер хранит ключ возврата сутки, а неизвестный результат обнаружен через двое суток. Объясните безопасные повторы, сверку, владельца восстановления, эскалацию и пределы гарантии. Правильный JSON основного кейса не доказывает правильность такого обоснования.

## Непроверяемые области
Модель предполагает доверенные callback, один платёж на заказ, общие часы, сохранённые ключи провайдера и возможность завершить его вызов после восстановления. Не моделируются частичные суммы, несколько платежей одного заказа, поддельные/чужие callback, много товаров, реальные уровни изоляции, несколько параллельных outbox-работников, долгие отказы провайдера, миграции схемы, нагрузка и эксплуатационные метрики. Внешний возврат не объявляется атомарным с локальной БД. Нарушение допущений требует нового контракта и отдельного доказательства.

## Использование в текущей аттестации

Семейство является одним из доступных вариантов для указанного направления и уровня; все семьи не выдаются в каждой попытке. Основной маршрут 0.16.0 — `work_sample_v3_balanced`, программа `competencies-2026-10-v14`:9 объективных заданий по трём областям, исходный кейс, отдельный проверяемый перенос и необязательное объяснение.

Для автоматического успеха одновременно требуются среднее короткого теста ≥ 70%, каждая основная область ≥ 50% при заполненной квоте и все обязательные проверки исходного кейса и переноса. Частичный рабочий балл полезен для разбора ошибок, но не компенсирует провал обязательной группы. Успешная аттестация выдаёт предварительную категорию автоматически; тренировка и неуспех сохраняют прошлую.

После этого предметного кейса обязательный перенос выполняется в другом ограниченном рабочем контексте того же направления и уровня с самостоятельным JSON-артефактом. Приведённые выше вопросы к объяснению дополнительны и не заменяют этот этап. Ручной структурированный разбор необязателен и не меняет автоматический проход v3.

Условия, семейство, версии модели/рубрики и эталоны заморожены в попытке. Ранее выданные версии продолжают проверяться собственным исполнителем; неизвестная версия даёт техническую паузу с сохранением ответов. Паспорт не содержит исходные ответы, скрытые эталоны или контакты. Пороги, сложность и соответствие профессиональным уровням не откалиброваны на людях.
