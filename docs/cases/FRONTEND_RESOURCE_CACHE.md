# Frontend: кеш списка для Junior/Middle

Текущий предметный кейс для **Junior/Middle**: идентичность кеша и актуальность асинхронного состояния. Семейство `frontend:resource_cache`, версия задания `resource-cache-v1`, модель/эталон `resource-cache-model-v1`, рубрика `resource-cache-rubric-v1`. Версии не переименованы в версию API: они сохраняются в каждой выданной попытке.

Проверяется ограниченный JSON-артефакт, а не запуск пользовательских программ или реальная инфраструктура. Сложность является авторской; профессиональная квалификация человека этим описанием не удостоверяется.

## Различия уровней и дефекты
| Уровень | Требуемое действие | Два исходных дефекта |
|---|---|---|
| Junior | Разделить ресурсы по фильтру/странице; кешировать только успешные ответы; соблюдать границу TTL | `page_collision`: страницы смешиваются. `cached_failure`: HTTP 500 превращается в готовый пустой список при следующей загрузке |
| Middle | Выполнить Junior и сохранить актуальность нескольких экранов при отмене/изменении данных | `global_stream`: общий текущий ID мешает второму экрану. `obsolete_generation`: поздний ответ возвращает данные после инвалидирования |

Junior автоматически не проверяет cancel/invalidate и несколько экранов. Middle получает ещё три поля плана и соответствующие сценарии; изменяются необходимые действия, а не только числа. Senior этим семейством не проверяется.

## Артефакт
Пример авторского плана Junior при TTL 30 секунд:

```json
{
  "key": ["filter", "page"],
  "cache_statuses": [200],
  "reuse": "fresh_only",
  "ttl_seconds": 30
}
```

Middle добавляет:

```json
{
  "key": ["filter", "page"],
  "cache_statuses": [200],
  "reuse": "fresh_only",
  "ttl_seconds": 30,
  "streams": "per_view",
  "invalidated": "discard",
  "cancelled": "discard"
}
```

Допустимый словарь указан кандидату: поля ключа filter/page, статусы 200/500, fresh_only/any, per_view/global, discard/accept. TTL — целое 1…300, а контракт попытки задаёт конкретное значение 10, 30 или 60. Условия выбирают два фильтра из open/closed/archived, страницы 1 и 2. Это девять сочетаний TTL/пары фильтров на каждый из четырёх дефектов — 36 сочетаний.

Порядок полей ключа несущественен: `["page", "filter"]` также принимается. Лишние поля, повторные JSON-ключи, недопустимые операторы/значения и ответы более 5 000 символов отвергаются. Поля checks нет; список названий тестов не заменяет поведение. Пользовательский код не исполняется.

## Контракт событий
| Событие | Ожидаемый эффект |
|---|---|
| load(view, filter, page, time, id) | Новый текущий ID экрана. Свежий кеш — ready без сети; иначе loading и один запрос. Старые отображаемые данные очищаются |
| response(id, status, items, time) | Только ответ текущего отправленного запроса. 200 — ready и кеш, включая пустой список. 500 — error/пустые данные без кеширования |
| invalidate(filter), Middle | Следующее поколение фильтра, удаление только его кеша, соответствующие экраны stale/пустые. Другие фильтры сохраняются |
| cancel(view), Middle | Этот экран idle/пустой. Поздний ответ отменённого запроса не меняет экран и кеш; другой экран продолжает работать |

Возраст кеша считается с момента успешного ответа. Свежесть: `time < cached_at + TTL`; ровно на границе нужен новый запрос. Ответ неизвестного ID, ответ на load из кеша и ответ уже заменённого запроса игнорируются. При invalidate даже ещё текущий ID не разрешает приём ответа старого поколения. После отмены/инвалидирования новый load должен работать.

Отмена не означает гарантированную остановку транспорта: модель намеренно допускает поздний callback. Ключ ресурса, текущий ID отдельного экрана и поколение фильтра решают разные задачи.

## Независимая проверка и контрпримеры
`execute()` применяет план участника. `oracle()` принимает только события и TTL контракта; не получает план или сохранённый reference_answer. Сравниваются экран, нормализованный кеш и ID отправленных запросов **после каждого события**. Конечное исправление состояния не скрывает промежуточное появление устаревших данных.

| Группа | Что проверяется |
|---|---|
| cache_identity | Разные фильтры/страницы, возврат к прежнему ресурсу, оба порядка завершения запросов, неизвестный ID |
| cache_http_errors | 500 без кеша и повторный сетевой запрос; кеширование пустого и непустого успешного 200 |
| cache_expiry | Возраст 0, TTL−1, TTL и TTL+1; отсчёт от ответа, не от начала запроса |
| independent_views, Middle | Два экрана и оба порядка ответов; запрос другого экрана не делает первый устаревшим |
| invalidation_epoch, Middle | Поздний ответ старого поколения, очистка готового кеша, сохранение другого фильтра и новая загрузка |
| cancelled_response, Middle | Поздний callback отменённого запроса не загрязняет кеш; другой экран и новый запрос работают |

Конкретные контрпримеры:

- После успешной страницы 1 загрузка страницы 2 должна дать loading и второй сетевой запрос. Ключ только filter вместо этого показывает данные страницы 1.
- После 500 повторный load должен отправить запрос. Кеширование 500 показывает ready с пустым списком и без сети.
- Запросы left/open и right/closed завершаются независимо. global отбрасывает ответ left после запуска right.
- После invalidate ответ old не меняет stale/пустые данные и кеш. accept восстанавливает устаревшее содержимое.
- Если после позднего old подождать истечения TTL и загрузить правильный ответ, конечные состояния могут совпасть. Полная трасса всё равно обнаруживает временное нарушение.

Junior имеет три группы, Middle — шесть. Балл — доля пройденных групп. Для автоматического принятия нужны **все**, поэтому 83,33% Middle с провалом независимых экранов не подтверждает категорию. Рецензент не может перекрыть этот провал.

## Дополнительное объяснение и пределы
Предметная рубрика сохраняет четыре критерия 0–3: корректность, независимые проверки, обоснование и пределы. Она служит дополнительной обратной связи, а не обязательным допуском текущей v3.

Junior объясняет полный ключ, успешный и ошибочный кеш, границу TTL. Middle различает ID запроса экрана, поколение ресурса и отмену; одного упоминания AbortController без проверки позднего callback недостаточно.

Вопрос Junior: добавлены сортировка и сброс страницы. Вопрос Middle: организация пользователя сменилась, а старый ответ ещё в пути. Нужны конкретные состояния и защита от смешения контекстов.

Не проверяются реализация React/TypeScript, DOM, доступность, настоящая сеть браузера, retry/backoff, дедупликация, согласование серверных версий и несколько вкладок. Учебная отмена не гарантирует остановку настоящего транспорта.

## Использование в текущей аттестации

Семейство является одним из доступных вариантов для указанного направления и уровня; все семьи не выдаются в каждой попытке. Основной маршрут 0.16.0 — `work_sample_v3_balanced`, программа `competencies-2026-10-v14`:9 объективных заданий по трём областям, исходный кейс, отдельный проверяемый перенос и необязательное объяснение.

Для автоматического успеха одновременно требуются среднее короткого теста ≥ 70%, каждая основная область ≥ 50% при заполненной квоте и все обязательные проверки исходного кейса и переноса. Частичный рабочий балл полезен для разбора ошибок, но не компенсирует провал обязательной группы. Успешная аттестация выдаёт предварительную категорию автоматически; тренировка и неуспех сохраняют прошлую.

После этого предметного кейса обязательный перенос выполняется в другом ограниченном рабочем контексте того же направления и уровня с самостоятельным JSON-артефактом. Приведённые выше вопросы к объяснению дополнительны и не заменяют этот этап. Ручной структурированный разбор необязателен и не меняет автоматический проход v3.

Условия, семейство, версии модели/рубрики и эталоны заморожены в попытке. Ранее выданные версии продолжают проверяться собственным исполнителем; неизвестная версия даёт техническую паузу с сохранением ответов. Паспорт не содержит исходные ответы, скрытые эталоны или контакты. Пороги, сложность и соответствие профессиональным уровням не откалиброваны на людях.
