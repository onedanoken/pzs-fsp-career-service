# Задания и подтверждение грейдов: передача разработчику

Текущий выпуск — **API 0.16.0 / schema 7**. Новые попытки используют `balanced-core-2026-v3`; правила текущего пути — [ASSESSMENT_POLICY](ASSESSMENT_POLICY.md). Новый маршрут `work_sample_v3_balanced` описан в [ASSESSMENT_V3](ASSESSMENT_V3.md). v2, v1 и legacy сохранены. Ниже остаётся техническая справка прежнего v2 для совместимости; выданные попытки не пересчитываются.

## Текущий путь v3 для новых попыток

1. Кандидат выбирает направление, уровень и тренировку/аттестацию. Сервер проверяет согласия, допуск, активную попытку и ограничения повторов.
2. `assessment_forms.py` собирает девять коротких заданий: три области по три наблюдения. `screening_operations.py` читает независимые авторские операции из `data/screening_core_operations.json`. Это конечный банк; его не следует называть неповторимым или защищённым от заучивания.
3. `work_samples.py` и `work_transfers.py` создают рабочий кейс и изменённое условие с отдельными проверяющими. Политика, условия, эталоны, источники и версии замораживаются в попытке.
4. Ответы сохраняются с optimistic version. При коллизии генератор проверяет повторные варианты до принятия или безопасного отказа; технический отказ не выдаёт провал.
5. Успех требует среднего screening >=70%, каждой основной области >=50%, всех original/transfer checks. Необязательный разбор не заменяет объективные проверки и не блокирует автоматическую категорию.
6. Аттестация выдаёт идемпотентный пилотный сертификат и паспорт; практика и неуспех сохраняют прошлую категорию. Повышение требует новой попытки. Исторические пути оцениваются по своим frozen policy.

Для нового семейства нужны схема артефакта, независимый эталон, допустимые решения, отрицательные проверки, изменённое условие и зарегистрированный dispatcher по версии. Нельзя менять ключ уже выданного задания или запускать произвольный пользовательский код в API-процессе. [Предметные кейсы](cases/README.md), [технические и синтетические проверки](VERIFICATION.md).

## Замороженный путь v2 для совместимости

1. Кандидат выбирает направление, предполагаемый грейд и practice/certification. Сервер проверяет согласия, отсутствие активной попытки, cooldown и 90-дневную политику.
2. Queue job создаёт три объективных задания, один bounded JSON-кейс, необязательный разбор. Условия, эталоны, источники, политика, blueprint и SHA замораживаются в payload.
3. Ответы автосохраняются с optimistic version; техническая ошибка не считается провалом. Пустое объективное задание получает 0; необязательная рефлексия не входит в процент.
4. `screening_avg = mean(трёх объективных оценок)`. `automatic_pass = screening_avg >= 70 AND all(work_checks)`. `strong = automatic_pass AND screening_avg >= 90`.
5. Аттестация выдаёт идемпотентный provisional сертификат и неизменяемый паспорт; тренировка — только результат. Неуспех сохраняет прошлую категорию. Выше/ниже — рекомендация, окончательный выбор добровольный.
6. Администратор может разобрать объяснение по общей рубрике; в v2 это обратная связь, которая не меняет автоматический проход. Апелляция имеет историю. Старый v1 по-прежнему требует собственный разбор по замороженной политике.

Процент сертификата хранит screening, кейс является отдельным обязательным гейтом. В паспорте явно указан способ оценки, границы и отсутствие ручного разбора. Нельзя выдавать этот балл за общую оценку владения профессией.

## QA: короткая проверка версии v7

Новые попытки QA в work_sample_v2_auto используют отдельный банк девяти сценариев: границы, таблица решений, свойства поиска, валидация API, идемпотентность, авторизация, воспроизведение дефекта, регрессия и окружение. Первые три задания выбираются из разных компетенций; ответ — выбор вариантов, без написания SQL или Python. Условия контракта даны в задаче. Код: backend/qa_screening.py; legacy/v1 и сохранённые старые попытки не переписываются. Это ограниченная пилотная проверка, не полная квалификация QA.

| Направление | Семейства | Пример нового ограничения старшего уровня |
|---|---|---|
| Backend | event_ledger, cursor_page | Ограничение баланса; snapshot/soft delete |

| ИБ | object_access, network_rules | Ownership/scope/expiry/block; сроки сетевых правил |

Intern/Junior задают базовый инвариант, Middle добавляет взаимодействие условий, Senior — дополнительные временные/конкурентные границы. Точная матрица в JSON; это предложение команды, не откалиброванный профессиональный стандарт. На каждое направление есть два разных рабочих семейства, не один кейс с новыми числами.

## Контракт кейса

Генератор формирует public prompt/artifact и private evaluator/expected/reference_answer/negative_answer/checks. Public API не отдаёт private. JSON ограничен 5000 символами, дубликаты ключей отклоняются, поля и типы проверяются точно; boolean не равен integer. Произвольный код/файлы/сеть не исполняются. Сравнение порядка ключей не влияет на результат.

Добавление семейства: определить наблюдаемую компетенцию и явные условия; написать чистую модель; зафиксировать корректный и известный дефектный ответ; добавить независимый оракул или честно обозначить модельную проверку; разделить development/holdout; проверить четыре уровня; обновить source/coverage; добавить новый evaluator version. Старые snapshots не мигрировать молча.

## API, безопасность и генератор

У клиента только серверные start/save/submit; нельзя выбирать legacy или присылать evaluation policy. Путь выбирается `FSP_ASSESSMENT_PATH=work_sample_v3_balanced|work_sample_v2_auto|work_sample_v1|legacy`. Результат и passport имеют собственные права. Повторный submit и job lease не создают дубликат сертификата. Отзыв согласия закрывает работодателю доступ.

Нейропровайдер `fsp-json-v1` меняет только разрешённый контекст по зафиксированным параметрам; schema/parameters/качество проверяются сервером. `mock=true` всегда помечен как reference protocol, neural_items=0. Реальная LLM необязательна и на стенде выключена; эталон вычисляет приложение. Источники pinned, персональные сведения не передаются.

## Проверка и ограничения

`pytest tests/test_auto_assessment.py tests/test_assessment_journey.py -q`; `python scripts/validate_assessment_v2.py --help`; браузер `scripts/browser_auto_closeout.py` выполняет шесть направлений на disposable данных.

3840 проверок условий не доказывают независимую сложность или квалификацию человека. Пороги 70/90 пилотные. Паспорт указывает область, дату, версии и способ оценки; SHA не является подписью ФСП. Для продуктивного расширения нужна отдельная калибровка на разрешённых участниках и оценка утечки стратегий. Технический прототип не зависит от поиска внешнего эксперта.


Дополнительные предметные семейства из ветки egor и их адаптация к автоматическому v3: [PARTNER_CASES_INTEGRATION](PARTNER_CASES_INTEGRATION.md). Исторические правила сохраняются.

## Дополнение выпуска 0.16.0

Новые формы используют `balanced-core-2026-v3`; путь `work_sample_v3_balanced` и правила выдачи сохраняются. `backend/grade_scenarios.py` содержит 72 собственных сценария ограничений грейда, `backend/screening_distractors.py` — правдоподобные альтернативы фундаментальным операциям. `screening_operations.py` объединяет исходный JSON и новые варианты версии v2. В каждом core фиксируются `generated_observation`, `professional_invariant`, `grade_decision`; роль и область входят в выданный item. У новых предметных choice-заданий четыре ответа. Эталон и объяснение лежат только в `private`, а разбор возвращается в result после завершения.

JSON операций и метаданные источников в контейнере находятся в `resources/`, поэтому постоянный или пустой `/app/data` не перекрывает банк. `assessment_catalog.source_snapshot()` выбирает ресурс образа; выданные снимки не переписываются. Новые поля не требуют миграции схемы 7.

Смена длины до 12 не включена: зарегистрированный точный анализ выявил увеличение допуска одной слабой области. `tests/test_assessment_policy_sensitivity.py` проверяет реальную функцию решения для всех 4 608 бинарных комбинаций. Все границы уровня остаются авторскими, не IRT-калиброванными.

`backend/certification_validity.py` задаёт общую проверку действующего результата для поиска, профиля и паспорта. Явный статус отзыва/истечения, `active=0`, невалидные поля и заданный источником истёкший `expires_at` закрывают текущую категорию. Возраст без явного истечения не отзывает её. Исторический просмотр собственной попытки остаётся доступным. Разделы UI объясняют различие категории направления и проверки отдельной технологии.

В `scripts/postgres_test_context.py` отдельно защищён случай заранее импортированного модуля БД: смена только environment не меняет сохранённый DSN. Контекст подменяет его на одноразовую схему и восстанавливает после выхода. API-сравнение дополнительно проверяет `current_schema()`. Обычные email-пути и новые формы проверяет `scripts/browser_final_journey.py`, без внешней почты и изменений рабочей БД.
